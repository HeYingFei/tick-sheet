# 用户管理与权限 设计方案

日期：2026-09-29

## 目标

增加用户管理界面（前后端），`admin` 为超级管理员，只有它能访问用户管理菜单。

## 现状与缺口

排查后确认，当前系统**没有任何权限模型**，本次不只是"加一个页面"：

| 项 | 现状 |
| --- | --- |
| `sys_user` 表 | 只有 `id / username / password_hash / nickname / avatar_url / status`，**无角色或权限字段** |
| `AuthInterceptor` | 只验 JWT 签名，通过后仅写入 `userId`——**只辨身份，不辨权限** |
| `AuthInterceptor` 漏洞 | **从不检查 `status`**。禁用账号不会踢掉已登录会话，对方可继续用到 token 过期（7 天） |
| `ErrorCode` | **无 403**，`BizException` 也没有 `forbidden()` |
| 注册 | `POST /api/auth/register` 完全开放，登录页有注册入口 |

"禁用不生效"这一条必须在本次一并补上，否则禁用功能只挡住新登录，与预期不符。

## 设计

### 1. 角色模型（迁移脚本 V4）

```sql
ALTER TABLE sys_user ADD COLUMN role VARCHAR(20) NOT NULL DEFAULT 'user';
COMMENT ON COLUMN sys_user.role IS '角色：admin-超级管理员，user-普通用户';
ALTER TABLE sys_user ADD CONSTRAINT ck_user_role CHECK (role IN ('admin', 'user'));

-- 把 admin 提为超管；万一没有同名账号，则取最早创建的账号，避免升级后无人可管
UPDATE sys_user SET role = 'admin'
WHERE id = COALESCE((SELECT id FROM sys_user WHERE username = 'admin' ORDER BY id LIMIT 1),
                    (SELECT id FROM sys_user ORDER BY id LIMIT 1));
```

角色判定看**字段**，不看用户名。改名不会丢权限，将来加「只读」「子管理员」也不必再改表。

`DataInitializer.ensureAdmin()` 建号时写入 `role = 'admin'`：全新库在 V4 执行时还没有账号，V4 的 UPDATE 不会命中，靠这一条兜底。

### 2. 鉴权模型：每请求查库

`AuthInterceptor` 验完 JWT 后，按 `userId` 载入用户的 `status` 与 `role`：

- `status != 1` → 401，**禁用立即生效**
- 把 `userId` 与 `role` 写入 `UserContext`

JWT 中仍只放 `userId`，不放 `role`。代价是每请求一次主键查询，本项目量级可忽略。

选择理由：把 `role` 塞进 JWT 虽然零额外查询，但禁用与改角色都要等 token 过期（最长 7 天）才生效——那会让"禁用"名不副实。

### 3. 后端接口

新增 `UserController` + `UserService`，全部挂在 `/api/users/**`：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/users` | 分页 + 关键字（用户名/昵称模糊匹配）。每行返回 id、用户名、昵称、角色、状态、创建时间。含管理员自身那一行 |
| POST | `/api/users` | 建号：用户名、昵称、初始密码；同时初始化该用户的默认配置 |
| PUT | `/api/users/{id}` | 改昵称 |
| PUT | `/api/users/{id}/password` | 重置密码（不需原密码） |
| PATCH | `/api/users/{id}/status` | 启用 / 禁用。沿用项目里 PATCH 子资源的约定（同任务状态） |

分页参数沿用现有约定（`page` / `size`，见任务列表接口）。

**权限**：新增 `AdminOnlyInterceptor`，注册到 `/api/users/**`，非 admin 一律 403。新增 `ErrorCode.FORBIDDEN(403, "无权访问")` 与 `BizException.forbidden()`。

**服务层约束**：

- **不能禁用自己**——否则会把自己锁在门外，只能改库恢复
- 用户名唯一，冲突返回 409
- 密码长度沿用 `@Size(min = 6, max = 64)`；用户名 `@Size(min = 2, max = 50)`
- 管理员**不能修改他人的角色**，本次不提供角色编辑接口。超管只有一个，避免出现"最后一个管理员把自己降级"的死局

### 4. 关闭开放注册

| 位置 | 处理 |
| --- | --- |
| `POST /api/auth/register` | 删除接口、`AuthService.register`、`RegisterRequest` |
| `WebConfig` | 白名单移除 `/api/auth/register` |
| 登录页 | 去掉注册入口，只留登录表单 |

"建号 + 初始化默认配置"的逻辑抽到 `UserService.createUser`，供管理员建号复用。

### 5. 前端

- `authStore` 增加 `role`；`LoginVO` 与 `getCurrentUser` 都回传 `role`
- `menuRoutes` 的用户管理项标 `meta.adminOnly: true`；`MainLayout` 渲染导航时按角色过滤
- 路由守卫拦截非管理员直达 `/users`。**这只是 UX，真正的拦截在后端**
- 新增 `views/UserManage.vue`：表格 + 关键字搜索 + 分页 + 新建/改昵称/重置密码对话框 + 启用禁用开关，复用现有 `.app-card` 与 `PageHeader`
- 导航位置：「系统设置」之后

### 6. 测试

`TestAuthSupport` 目前固定用 admin（`TEST_USER_ID = 1`）的身份，**测不了 403 那条路径**，需扩展为支持"以指定用户身份发请求"。覆盖：

- 非管理员访问 `/api/users` → 403
- 管理员建号 → 新用户能登录、默认配置已初始化
- 管理员禁用自己 → 被拒绝
- 用户名冲突 → 409
- 被禁用用户的 token 立即失效 → 401
- 关闭注册后 `POST /api/auth/register` → 404

## 边界（本次不做）

- 不做角色编辑，不引入除 `admin` / `user` 之外的角色
- 不做用户删除。页面上只有启用/禁用，避免误操作丢掉真实数据
- 不做多级管理员、菜单级细粒度权限
- 管理员看不到他人的任务数据——数据隔离维持现状，用户管理只管账号
- **重置密码不会踢掉对方已登录的会话**。要让重置后的旧会话失效，需要引入 token 版本号或黑名单，本次不做；需要立即失效时，改用「禁用 → 再启用」
- 列表里管理员自身那一行不显示禁用开关（服务端也会拒绝，前端隐藏只是少一次无谓报错）

## 验证方式

1. 迁移在真实库执行成功，`admin` 的 `role` 为 `admin`
2. 用 admin 登录可见「用户管理」菜单，普通用户看不到，且直达 `/users` 被拦
3. 普通用户直接调 `GET /api/users` 返回 403
4. 管理员建号后，新账号能登录且设置页可读到自己的默认配置
5. 禁用某用户后，该用户**已登录的会话下一次请求即返回 401**
6. 管理员禁用自己 → 拒绝
7. 登录页不再有注册入口，`POST /api/auth/register` 返回 404
